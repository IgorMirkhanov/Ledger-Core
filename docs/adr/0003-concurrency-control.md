# ADR-0003: READ COMMITTED + пессимистичные блокировки строк

**Статус:** принято

## Контекст
Переводы изменяют 2–4 счёта. Нужна защита от lost update и double spend.

## Варианты
1. **SERIALIZABLE** + ретраи на `40001`. Корректно «из коробки», но при высокой конкуренции
   на горячих счетах много откатов; поведение хуже предсказуемо под нагрузкой.
2. **Оптимистичные блокировки** (version) на счетах. Много конфликтов на горячих счетах → ретраи.
3. **READ COMMITTED + `SELECT ... FOR UPDATE` в порядке id**. Предсказуемо, без ретраев,
   очередь на строке вместо откатов. Дедлоки исключены единым порядком блокировок.

## Решение
Вариант 3 для счетов и холдов. Оптимистичная версия используется для `transfers`
(где конкуренция низкая, а держать блокировку во время gRPC-вызова нельзя).
Плюс defense-in-depth: CHECK-constraint на неотрицательный доступный остаток и deferred-триггер баланса.

## Последствия
+ Тест «1000 параллельных переводов» проходит без ретраев, сумма сходится.
− Горячий счёт (`settlement.RUB`) сериализует все депозиты. Решение на будущее:
  N суб-счетов `settlement.RUB#k`, выбор по hash(key) % N, сверка суммирует их.
