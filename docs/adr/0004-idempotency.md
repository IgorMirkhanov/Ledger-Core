# ADR-0004: Идемпотентность в той же транзакции, что и операция

**Статус:** принято

## Решение
- Ключ `(scope, key)` вставляется в `idempotency_keys` **внутри** бизнес-транзакции.
- Конкурентный дубль блокируется на уникальном индексе до COMMIT/ROLLBACK первого.
  После COMMIT видит готовый ответ; после ROLLBACK выполняет операцию сам.
  Статус `in_progress` не нужен.
- Хранится `sha256` детерминированно сериализованного запроса: другой payload с тем же ключом → ошибка.
- Ответ сохраняется (JSON результата use case), replay возвращает его без повторного выполнения.
- Межсервисные вызовы saga используют детерминированные ключи `transfer:<id>:<step>`.
- Клиентский ключ — недоверенный ввод: в БД он хранится как `<owner_id>/<key>` (`idempotency.Namespace`).
  Иначе одинаковые ключи разных пользователей сталкиваются в `PK (scope, key)`.
  Внутренние ключи хранятся как `svc:transfers/transfer:<id>:<step>`.
- Факт replay передаётся из use case в transport через ctx (`WithReplayTracker` / `MarkReplayed`)
  и отдаётся клиенту заголовком `Idempotent-Replayed: true`.
- Redis для идемпотентности **не используется**: он не транзакционен с Postgres,
  возможна ситуация «ключ записан, операция откатилась».

## Последствия
+ Строгая гарантия exactly-once эффекта для одной БД.
− Долгий запрос держит дубли в ожидании блокировки (ограничено statement_timeout/deadline).
− Таблица растёт → TTL 48h и чистка батчами.
